Before the pause

Correlation creates an Approval record

The pending request contains ID, action type, target, reason, complete evidence, proposing Agent, and timestamp. It is stored in MongoDB and returned into graph state before the Approval node runs.

Pure gate

interrupt() suspends execution

The Approval node passes pending_approval outward and waits. The checkpointer saves the graph position and state under the Investigation’s thread_id. Crucially, the node does not write a decision or execute any action before the interrupt.

Why purity matters

On resume, interrupted node execution may replay from its beginning. Keeping side effects after the interrupt prevents a duplicated database write or recovery call simply because execution resumed.

After the operator

The decision resumes the same thread

The API validates that the Approval exists, belongs to the Investigation, and is pending. It queues workflow.resume(id, approved). Command(resume=True|False) supplies the interrupt result. The next node records the decision, then the conditional router reads approval_result.

Approved

record_decision → execute → report. Controlled HTTP recovery runs before the Report.

Rejected

record_decision → rejected. No path through execute; Report says no action ran.

Safety proof

Make the claim from reachability

Do not say “the prompt tells the agent to ask.” Say: the only incoming edge to execute is the approved mapping from the conditional router; the rejected mapping terminates through a different node. Safety is encoded in graph topology, not model compliance.

Not complete idempotency

The gate is safe, but the API can race

The decision endpoint checks status == pending, then starts resume asynchronously. Two concurrent requests may both see pending before either resume records a decision. Recovery HTTP calls also have no idempotency key. A production version needs an atomic pending→decided claim and idempotent execution.

Which placement makes the interrupt gate replay-safe?

Teach it back

Prove, from code structure, that rejection cannot execute remediation.

Model answer
The interrupt yields the operator’s boolean. The next node persists approved or rejected. The router maps only approved to execute; rejected maps directly to _rejected_report, which terminates. No other edge enters execute, so rejection cannot reach recovery.
