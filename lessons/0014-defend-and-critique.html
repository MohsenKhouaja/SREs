60-second pitch

SREs is a local, evidence-first incident-response lab. An API deliberately activates one of three failures in two instrumented sample services. A checkpointed graph runs Log, Metrics, and Event specialists in parallel, joins their Findings for deterministic correlation with optional LLM phrasing, then interrupts before any controlled remediation. The operator approves or rejects; only approval can reach execution. MongoDB stores product records and checkpoints, an in-memory hub streams live SSE updates, and a Next.js interface preserves the path from simulation through Evidence, decision, and Report.

Defensible choices

Safety is structural

Explicit branch reachability and a pure interrupt gate are stronger than prompt-only policy.

Evidence remains inspectable

Findings retain timestamp, source, message, and raw tool envelope.

Determinism lowers demo fragility

No API key is required; provider failure has a fallback.

Boundaries support tests

Store protocol, app factory, and memory checkpoint make the core executable without nine services.

UX matches the risk model

Simulation, Investigation, Approval, and Report are separate, readable stages rather than chat messages.

Production sequence

Improve safety before autonomy

  1. Secure and serialize decisions

    Authentication, RBAC, audit identity, atomic Approval claim, idempotency keys.

  2. Make execution durable

    Durable worker/lease model, startup recovery, explicit task ownership, replica-safe events.

  3. Validate Evidence and outcomes

    Require successful sources, confidence policy, real change events, post-remediation verification, distinct failure status.

  4. Then broaden intelligence

    Dynamic query planning, constrained tool selection, structured model output, citation checks, evaluation suite.

Interview practice

Answer with Claim → Code → Trade-off

Why a graph instead of ordinary service functions?

Claim: explicit long-lived control flow. Code: fan-out/join, interrupt/checkpoint, conditional branch. Trade-off: framework complexity for visibility and resumability.

Is this production-ready?

Claim: intentionally a local lab. Code: controlled flags, no auth, process-local tasks/events. Trade-off: reproducibility and safety over scale and integration realism.

What would you change first?

Claim: atomic authorized Approval. Code: current check then background resume race. Trade-off: correctness and auditability before more autonomous capability.

Record a five-minute answer covering purpose, topology, lifecycle, state, Evidence, AI boundary, safety, persistence, UX, tests, two strengths, three risks, and your first improvement.

Scoring rubric
Strong: precise domain language; separates three planes and three state systems; proves branch safety from edges; bounds the LLM; distinguishes real and synthetic Evidence; cites files/functions; admits local-lab limits; prioritizes improvements by risk. Weak: says “agents analyze everything,” treats SSE as durable, claims retries cover returned errors, claims rejection safety is prompt-based, or proposes more AI before authorization/idempotency.
