Working state

One typed document moves through the graph

IncidentState is not the MongoDB Investigation document. It is the graph’s working state: identity, three Finding lists, analysis, Approval data, execution result, Report, status, and accumulated agent steps.

class IncidentState(TypedDict): incident_id: str log_findings: Annotated[list[Finding], operator.add] root_cause: str pending_approval: ApprovalRequest | None ...

TypedDict describes expected keys to developers and type checkers. It does not create an object with methods; at runtime the state is dictionary-shaped.

Node contract

Nodes return updates, not a replacement world

The Log Agent reads scenario and incident_id, then returns only log_findings and agent_steps. Correlation later reads all three Finding lists and adds analysis and Approval fields. This keeps each node’s write surface narrow.

CRUD instinct

Load one entity, mutate fields, save the whole object.

SREs graph

Receive current state, compute a partial update, let the runtime merge it.

Parallel safety

Three list fields have explicit merge rules

Annotated[..., operator.add] tells the graph to append list updates. Without a reducer, two parallel writers to one field could conflict or overwrite. SREs uses reducers on each collector-specific Finding list and on agent_steps.

Subtle point

Collectors actually write different Finding fields, so they already avoid direct collision. The reducers also make repeated or future parallel contributions accumulate. agent_steps genuinely receives updates from multiple nodes.

Reading technique

Ask “who writes, who reads?”

Use the state ownership table. If you add a field, identify its initial value, writer node, reader node, merge policy, checkpoint behavior, and whether it also belongs in the product Store.

What prevents concurrent list updates from overwriting?

Teach it back

Explain why IncidentState, the Investigation record, and one Agent record are not the same object.

Model answer
IncidentState is checkpointed execution data shared by graph nodes. The Investigation record is the product-level query model returned by APIs. Agent records separately support per-agent UI status and Findings. Some information is intentionally duplicated because each representation serves a different consumer.
