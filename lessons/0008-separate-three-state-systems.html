Product query model

Store answers what the UI needs now

The Store protocol covers Investigations, per-Agent states, and Approvals. MongoStore creates unique identity indexes plus status/investigation lookup indexes. InMemoryStore implements the same behavior behind an async lock for tests.

The detail API assembles one response from three collections. Datetimes are serialized and Mongo’s internal _id is removed.

Execution continuation

The checkpointer answers “where was the graph?”

Production uses MongoDBSaver; tests use InMemorySaver. Checkpoints contain framework execution state, including the paused interrupt. They are selected separately from Store, even though both production implementations use MongoDB.

A product Investigation document saying awaiting_approval cannot itself resume the graph. Resume requires the checkpoint associated with the same thread_id.

Low-latency experience

EventHub answers “what just happened?”

Each Investigation has an in-memory history and a set of subscriber queues. A new subscriber receives current-process history, then waits for new events. SSE converts each event to data: JSON\n\n and sends a comment keep-alive every 15 seconds.

Trade-off

History is unbounded and process-local. A restart loses it; multiple backend replicas would have different histories; and a full subscriber queue can make publish wait.

Which mechanism resumes a paused Approval?

Teach it back

A browser reconnects after a backend restart. Explain what it can recover, what it cannot replay, and what is required to resume Approval.

Model answer
REST can reconstruct product state from MongoDB. The old process’s EventHub history and task handles are gone, so live events cannot be replayed from there. If the Mongo graph checkpoint exists, an Approval decision can resume the paused thread, though the application has no general startup worker that automatically recovers arbitrary running tasks.
