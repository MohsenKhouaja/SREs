SREs is the control plane. The sample services are the system it investigates. Prometheus and Loki sit between them as evidence stores. MongoDB stores SREs’s own operational state, not the sample application’s users or cache.

Traffic

Do not merge these four paths

Control:

Backend POSTs failure toggles and approved recovery calls to the sample services.

Telemetry production:

Sample services push structured logs to Loki and expose /metrics for Prometheus to scrape every five seconds.

Evidence retrieval:

Workflow tools query Loki and Prometheus after a warm-up period.

Operator experience:

Browser uses REST for durable state and SSE for immediate activity updates.

See the printable system and code map for ports and ownership.

Safety boundary

The “remediation” is deliberately narrow

The backend never mounts the Docker socket and never runs arbitrary commands. Recovery only POSTs to bundled simulation endpoints: disable a Redis or slow-database flag, or switch v2 to v1. This is a lab for reasoning about operational control, not a production actuator.

Interview answer: “The topology isolates the orchestration problem from real infrastructure risk. It preserves realistic signals and human approval while constraining side effects to in-process sample-service flags.”

Model structure
Control plane: frontend, backend, MongoDB. Observability: Prometheus and Loki. Controlled lab: two sample services, Redis, PostgreSQL. Backend controls failure flags, sample services emit signals, observability stores them, tools query them, and REST/SSE expose the Investigation to the browser.
