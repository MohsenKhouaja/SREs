One image, two roles

SERVICE_KIND creates API and payment services

Both containers run the same file. api exposes users, products, orders, slow query, Redis and PostgreSQL behavior. payment exposes payment creation/read behavior and Redis. Each process has its own SimulationState, so the backend toggles both where necessary.

Continuous signals

A background loop emits telemetry every two seconds

Healthy mode increments 200 requests, records short duration, sets Redis active, and pushes an INFO log. Failure modes instead emit fixed error counts, eight-second observations, or v2 errors. Prometheus scrapes exposed counters, gauges, and histograms every five seconds. Logs are actively pushed to Loki with nanosecond timestamps and JSON payloads.

Realistic enough, not production-real

Failures change application state, not infrastructure

Redis remains running; the app flag refuses operations. PostgreSQL remains healthy; the API sleeps. No deployment occurs; middleware returns 500 for ordinary /api/ paths when version is v2. This gives repeatable signals without destructive infrastructure operations.

Evidence nuance

The synthetic loop emits signals even if no user traffic occurs. Bad deployment may count both synthetic and actual middleware failures. The Event Agent does not read a deployment system; it constructs timestamps from Scenario activation.

Model answer
The backend enables slow-db only on sample-api. The app sleeps about eight seconds and observes PostgreSQL/API latency while logging the slow SELECT. Prometheus stores histogram samples and Loki stores the log. Collectors query those signals; Correlation proposes disabling slow mode, and approved execution POSTs enabled=false to sample-api.
