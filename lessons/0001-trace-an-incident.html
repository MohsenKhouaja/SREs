The anchor

One sentence first

SREs deliberately breaks a sample service, collects three kinds of evidence in parallel, correlates them into a proposed root cause and remediation, pauses for a human decision, then either performs the controlled recovery or closes without action, and finally stores a report.

That sentence is the whole product. Every important file exists to make one part of it happen safely, visibly, or durably.

Open the project glossary whenever an Incident, Investigation, Finding, Evidence, Approval, or Remediation term feels interchangeable. In SREs, they are not.

Bridge from CRUD

The request returns before the work ends

A familiar CRUD request

Browser sends request → route validates → service reads or writes → database commits → response returns.

→

This Investigation request

Browser sends request → API creates a record and background task → response returns 202 with an ID → workflow continues and streams progress.

The shift is not “CRUD versus AI.” The shift is short request/response work versus a long-lived, stateful execution that must pause and later resume.

The execution trace

Follow the bad-deployment scenario

  1. The UI starts the Scenario

    The Simulate screen posts {auto_start_investigation: true}, receives an Investigation ID, and navigates to its live page.

    Source: simulate/page.tsx · trigger()

  2. The API first creates the failure

    For bad-deployment, it tells both sample services to switch to broken v2 behavior. Then it creates the durable Investigation and five waiting agent records.

    Source: main.py · simulate() and _trigger_failure()

  3. The API starts background execution

    workflow.start() creates an asynchronous task, while the route returns 202. After a telemetry warm-up, the task invokes the graph with a fresh IncidentState.

    Source: workflow.py · start() and _run_initial()

  4. Three collectors fan out

    Log queries Loki, Metrics queries Prometheus, and Event builds a causal timeline. They start from the same graph state and each returns only its own Findings.

    Source: workflow.py · _build_graph(), _log_agent(), _metrics_agent(), _event_agent()

  5. Correlation waits for all three

    The join edge prevents Correlation from running early. It reads all Findings, ranks fixed hypotheses, chooses project-specific fallback wording, optionally asks one configured model to refine only the root-cause sentence, and creates a pending Approval.

    Source: workflow.py · _correlation_agent()

  6. The graph stops at a pure approval gate

    interrupt() checkpoints the run and returns control. The node itself writes no decision and performs no remediation, so replaying it cannot duplicate an external side effect.

    Source: workflow.py · _approval_node()

  7. The operator chooses the only risky branch

    The approval screen posts approve or reject. The backend resumes the same checkpoint. Approval reaches execute and switches both services to v1; rejection reaches a separate report path that never executes remediation.

    Source: approvals/[id]/page.tsx · decide()

  8. A durable Report closes the Investigation

    Both branches produce a Report. The approved path includes execution results; the rejected path explicitly says that no operational action ran.

    Source: workflow.py · _report_agent() and _rejected_report()

Remove the magic

What “agent” means in this codebase

Each user-visible Agent is a narrow application function registered as a graph node. The graph—not an LLM—decides their execution order. Log, Metrics, and Event perform predefined operations. Correlation has predefined hypotheses and deterministic scenario fallbacks. A configured LLM can refine one sentence, but failure falls back safely.

Interview distinction: SREs is best described as a deterministic, stateful orchestration with specialist agent-shaped nodes and optional LLM-assisted phrasing. It is not a collection of autonomous models freely choosing tools and delegating work.

This distinction is supported by workflow.py, where nodes and edges are registered explicitly, and llm.py, where disabled or failed model calls return the deterministic fallback.

Interview-grade detail

Three kinds of state serve three jobs

Product records

Investigations, agent states, approvals, and reports live behind Store. MongoDB is normal runtime storage; memory is used in tests.

Graph checkpoint

The checkpointer preserves the paused execution position and graph state. The Investigation ID is also the graph thread_id.

Live event stream

EventHub feeds immediate SSE updates to connected browsers. It is process-local and is not the durable source of truth.

A page refresh can reconstruct the Investigation from product records. A resume needs the graph checkpoint. A smooth live UI uses the event stream. Those are related, but they are not substitutes.

Storage-strength exercise

Give the 60-second interview answer

Without looking back, answer: “What happens end-to-end when a user runs the bad-deployment scenario?” Include the trigger, parallel collectors, join, approval pause, both decision branches, and final report.

Reveal a strong model answer
The frontend posts the bad-deployment Scenario to the backend. The backend switches both sample services to broken v2 behavior, creates durable Investigation and agent records, starts a background graph task, and returns the Investigation ID. Log, Metrics, and Event nodes then collect Loki, Prometheus, and timeline Findings in parallel; a join ensures Correlation sees all three streams. Correlation ranks hypotheses, establishes a root cause, creates a pending remediation Approval, and the graph checkpoints and pauses. An operator decision resumes that same graph: approval routes to the controlled v2-to-v1 rollback, while rejection routes directly to a no-action report. Either branch ends by persisting a Report and publishing live status events to the UI.
